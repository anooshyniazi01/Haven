# Haven — Data Dictionary

## 1. Purpose

This document defines the meaning, format, validation rules, and interpretation of important data used throughout Haven.

The frontend, backend, database, AI analysis pipeline, reports, and tests must use consistent definitions.

The database schema defines how data is stored. This document defines what that data means.

## 2. Identifier Fields

### `id`

- Meaning: Unique identifier for a database record.
- Format: UUID string.
- Generated by: Backend.
- Rules: Must be unique and must not be accepted blindly from client input.
- Display: May be shown in a record's technical details when useful.

### `analysis_id`

- Meaning: Identifier of an associated analysis record.
- Format: UUID string.
- Nullable: Yes, when an evidence item has no associated analysis.
- Rules: When provided, the referenced analysis must exist.

### `evidence_id`

- Meaning: Identifier of a saved evidence record.
- Format: UUID string.
- Rules: Must reference an existing evidence record when used in an incident relationship.

### `incident_id`

- Meaning: Identifier of a documented incident.
- Format: UUID string.
- Rules: Must reference an existing incident when used in an incident-evidence relationship.

## 3. File Metadata

### `original_filename`

- Meaning: User-facing name of the uploaded file.
- Source: Client-supplied filename, treated as untrusted input.
- Rules: Length-limited, safely encoded, and never used directly as a filesystem path.
- Display: May be shown in the interface and report.
- Privacy: Avoid placing sensitive filenames in unnecessary logs.

### `storage_key`

- Meaning: Internal identifier used by the storage layer to locate a managed file.
- Generated by: Backend.
- Rules: Must not contain unsafe path components or expose an absolute filesystem path.
- Display: Must not be exposed as a public download URL.

### `file_size_bytes`

- Meaning: Size of the file in bytes.
- Type: Non-negative integer; accepted files must have a size greater than zero.
- Source: Actual uploaded bytes, measured by the backend.
- Rules: Must satisfy the configured upload-size limit.
- Display: May be converted into KB or MB for readability.

### `mime_type_detected`

- Meaning: Media type determined through server-side file inspection.
- Type: String.
- Rules: Must not be copied blindly from the request's MIME header.
- Limitation: A detected media type alone does not guarantee that a file is safe or valid for every operation.

### `sha256`

- Meaning: SHA-256 digest calculated from a specific file's bytes.
- Type: 64 hexadecimal characters.
- Source: Backend hashing using the actual byte sequence.
- Rules: Recalculate when verifying a stored file.
- Interpretation: Matching hashes indicate matching byte sequences for the compared files.
- Limitation: A hash does not establish authenticity, ownership, capture time, truthfulness, or chain of custody.

## 4. Analysis Lifecycle

### `status`

Meaning: Current lifecycle state of an analysis.

Allowed values:

- `uploaded`: The file has been accepted and registered but has not completed analysis.
- `processing`: The analysis operation is currently running.
- `completed`: Analysis completed successfully and its result was persisted.
- `failed`: Analysis could not complete successfully.

Rules:

- Status transitions must be validated by the backend.
- A failed operation must never be represented as completed.
- A completed status requires a persisted result consistent with the selected analysis method.
- A result must not be displayed as final while processing is incomplete.

### `created_at`

- Meaning: Time the analysis record was created.
- Type: DateTime in UTC.
- Source: Backend.
- Interpretation: Record creation time, not the original image capture time.

### `completed_at`

- Meaning: Time the analysis successfully completed.
- Type: Nullable DateTime in UTC.
- Rules: Must remain null if analysis has not completed successfully.

### `updated_at`

- Meaning: Time the record was last modified.
- Type: DateTime in UTC.
- Rules: Update whenever a relevant persisted field changes.

## 5. AI Analysis Fields

### `analysis_method`

- Meaning: Name or description of the actual analysis approach used.
- Examples: A specific evaluated classifier or a documented forensic-analysis method.
- Rules: Must identify the method that was genuinely executed.
- Limitation: The method's name alone does not establish accuracy.

### `model_name`

- Meaning: Identifier of the model used, when a model is involved.
- Type: Nullable string.
- Rules: Must match the actual model loaded for inference.

### `model_version`

- Meaning: Version, checkpoint identifier, or other reproducible model reference.
- Type: Nullable string.
- Rules: Record the strongest available identifier without inventing version information.

### `result_label`

- Meaning: Categorical output produced by the selected analysis method.
- Type: Nullable string.
- Rules: Allowed labels must be defined in `AI_SPEC.md`.
- Display: Use clear wording that explains what the label means.
- Limitation: A label is a model or method output, not independent proof of authenticity.

### `result_score`

- Meaning: Numeric score returned by the configured analysis method.
- Type: Nullable floating-point number.
- Rules: Store only an actual output from the method.
- Validation: Enforce the method's documented numeric range.
- Missing value: Store as null, not zero.
- Limitation: A score must not be interpreted as a probability without appropriate calibration and supporting evaluation.

### `score_type`

- Meaning: Describes how `result_score` should be interpreted.
- Examples: Raw logit, similarity score, anomaly score, uncalibrated confidence score, or calibrated probability.
- Rules: The description must match the method's documentation.
- Display: Explain the score's meaning and direction where relevant.
- Limitation: Scores from different methods must not be compared as if they shared a common scale unless justified.

### `explanation`

- Meaning: Human-readable explanation of the analysis result.
- Source: Actual analysis output and documented method behavior.
- Rules: Must not invent evidence, certainty, model reasoning, or causal explanations.
- Display: Separate observations from interpretations and limitations.
- Limitation: An explanation generated from model outputs is not necessarily a complete or faithful account of the model's internal reasoning.

### `limitations_json`

- Meaning: Structured list of limitations relevant to the specific analysis.
- Type: Valid JSON array of strings.
- Examples: Dataset limitations, unsupported file conditions, uncertainty, or known model weaknesses.
- Rules: Must contain meaningful limitations rather than generic text copied without review.

### `error_code`

- Meaning: Machine-readable identifier for an analysis failure.
- Type: Nullable string.
- Rules: Must use a documented error code.
- Privacy: Must not contain sensitive evidence, secrets, stack traces, or filesystem paths.

## 6. Evidence Metadata

### `description`

- Meaning: Optional user-provided context about an evidence item or incident.
- Type: Nullable text.
- Rules: Treat content as untrusted input and escape it when rendering.
- Privacy: Avoid requesting unnecessary sensitive information.

### `linked_at`

- Meaning: Time an evidence record was linked to an incident.
- Type: DateTime in UTC.
- Interpretation: Indicates when the application recorded the relationship, not when the evidence was created or received.

### Evidence versus analysis

An uploaded image and a saved evidence item are different concepts:

- An analysis record tracks an upload and its analysis lifecycle.
- An evidence record tracks an item deliberately preserved in the Evidence Vault.
- An incident-evidence relationship records that a saved evidence item was associated with a documented incident.

Saving an image to the Evidence Vault must not silently change the original file bytes.

## 7. Incident Fields

### `title`

- Meaning: Short user-provided label for an incident.
- Type: Required string.
- Rules: Must not be empty after trimming whitespace and must satisfy a configured length limit.

### `incident_date`

- Meaning: User-provided date on which the incident reportedly occurred.
- Type: Nullable date.
- Rules: Must use a valid date.
- Interpretation: This is a reported date, not independently verified fact.
- Limitation: Do not substitute the record creation date when the incident date is unknown.

### `status`

Meaning: Current user-managed incident tracking state.

Allowed values:

- `open`: The incident is being tracked.
- `documented`: The user has recorded relevant details.
- `resolved`: The user has marked the incident as resolved.

Rules:

- This status describes the user's tracking workflow.
- It does not indicate a legal finding or independently verified outcome.
- Status changes must be validated by the backend.

### `created_at`

- Meaning: Time the incident record was created.
- Type: DateTime in UTC.
- Interpretation: Not necessarily the time the reported event occurred.

### `updated_at`

- Meaning: Time the incident record was last updated.
- Type: DateTime in UTC.
- Rules: Update when incident information changes.

## 8. Dashboard Metrics

### `total_analyses`

- Meaning: Number of analysis records included by the dashboard's defined counting rule.
- Source: Database query.
- Rules: Define whether failed records are included; by default, this metric counts all analysis records.

### `saved_evidence_items`

- Meaning: Number of records in the Evidence Vault.
- Source: Database query.
- Rules: Count persisted evidence records, not uploaded files that have not been saved to the vault.

### `open_incidents`

- Meaning: Number of incident records whose status is `open`.
- Source: Database query.
- Rules: Must reflect current persisted status values.

### `recent_analyses`

- Meaning: Most recent analysis records selected for dashboard display.
- Ordering: Newest record first, using a stable secondary ordering when timestamps match.
- Rules: Return only fields needed by the interface.

All dashboard metrics must use actual database records. Empty data must produce genuine empty states.

## 9. Dates and Time Zones

- Store timestamps in UTC.
- Serialize timestamps in ISO 8601 format.
- Use explicit date-only fields for incident dates where a time is not known.
- Convert timestamps to local display time only in the frontend.
- Never describe a record timestamp as an image capture timestamp unless that capture time was independently available and its source is documented.

## 10. Missing, Invalid, and Uncertain Values

- Use `null` for unavailable optional values.
- Use empty arrays for collections with no items.
- Use empty strings only where explicitly allowed; required descriptive fields must not be blank.
- Do not replace missing scores with zero.
- Do not invent timestamps, model versions, labels, or explanations.
- Reject invalid status values and malformed identifiers.
- Display uncertainty in understandable language instead of hiding it.

## 11. Sensitive Data and Logging

- Treat uploaded images, filenames, descriptions, incident notes, and analysis outputs as potentially sensitive.
- Do not log raw file content or full incident descriptions by default.
- Do not place sensitive content in exception messages returned to the frontend.
- Avoid collecting unnecessary personal identifiers.
- Keep evidence storage separate from publicly served assets.
- Document retention and deletion behavior before implementing permanent deletion.

## 12. Cross-Application Consistency

The following rules apply across the frontend, backend, database, and reports:

1. A displayed status must match the persisted status.
2. A displayed score must preserve the documented score meaning.
3. A hash must refer to a specific byte sequence.
4. A timestamp must identify the event it actually represents.
5. A saved evidence item must correspond to a real stored file.
6. An incident's status must not be presented as an independently verified outcome.
7. A completed analysis must contain a genuine, persisted result.
8. Limitations must remain visible in the report and interface.
9. Unknown or missing information must remain unknown rather than being fabricated.

## 13. Maintenance

When a field is added, removed, renamed, or reinterpreted:

- Update the database schema.
- Update this data dictionary.
- Update the API specification where relevant.
- Update the AI specification and evaluation documentation where relevant.
- Add or revise tests.
- Update existing records through an explicit migration if necessary.

This document must describe the implemented behavior, not aspirational behavior that has not been built or verified.
